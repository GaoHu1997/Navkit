## 一、A 类：会直接让用户数据/功能出错的（建议修）

### A1. `count_query_page` 在 MySQL 解码失败 —— ✅ 确认（现场复现）

| 项 | 内容 |
|---|---|
| 证据 | 现场调用返回：`error occurred while decoding column 0: mismatched types; Rust type Option<String> (as VARCHAR) is not compatible with SQL type BIGINT`。同一 SQL 走 `execute_sql` 时 COUNT 正常返回 `"10000"` |
| 根因 | `src-tauri/src/db.rs:263` `sql_scalar()` 对 MySQL 用 `query_scalar::<_, Option<String>>`，而 MySQL 驱动把 `COUNT(*)` 报为 `BIGINT` 类型，sqlx 0.8 类型检查拒绝解码（`transfer.rs` 里已为此类问题做过 u64/字符串双路兜底，此处没做） |
| 不修的后果 | **查询页"总行数"永远显示"统计中/未知"**，页码输入框与"末页"按钮**永久禁用**（代码里明确 `disabled` 直到有精确总数）。1 万行和 1 亿行表现一致——用户无法跳到任意页，只能一页页点，大结果集浏览体验直接废掉一半 |
| 影响面 | MySQL/MariaDB/TiDB（MySQL 协议族）；SQLite/PG 未验证但同函数共用 |
| 改动成本 | **小**。改 `sql_scalar` 增加整数/无符号分支（先试 `Option<u64>` 再退 `Option<String>`），或对 count 走 `execute_sql` 已有路径取首格文本。约 10~30 行 + 单测 |
| 备注 | 报告里写的"1万→1亿 100% 复现"成立；这不是测试环境问题 |

### A2. 运行 SQL 文件拒绝含 `CREATE DATABASE`/`USE` 的文件 —— ✅ 确认（三轮未修）

| 项 | 内容 |
|---|---|
| 证据 | `src-tauri/src/batch_sql_reader.rs:145` 显式拒绝：`SQL 不能改变数据库/身份/服务器授权范围` |
| 这是设计还是缺陷 | **是刻意的安全门禁**（防止脚本劫持连接改库/提权），不是 bug。但它**挡住了最常用的迁移场景**：mysqldump 导出的文件常带 `CREATE DATABASE`/`USE` |
| 不修的后果 | 用户拿到别人给的 .sql 迁移脚本，**只能手工删掉前几行才能导入**；对不熟悉 SQL 的用户等于功能不可用。这是报告里唯一连续三轮都被用户实际卡住的点 |
| 改动成本 | **中**。需要一个"受控管理脚本"模式：预扫描 → 提取要改动的库名清单 → 弹窗让用户确认 → 授权绑定到本次执行 → 只放行清单内的声明、其余仍拒绝。涉及前端确认 UI + 后端授权传递，约 200~400 行 |
| 建议 | 若不做，至少在报错文案里**明确告诉用户"请删除 CREATE DATABASE/USE 语句后重试"**（10 分钟成本，立刻缓解） |

### A3. 亿级单文件导入吞吐塌陷 —— ✅ 确认（实测 3.2 小时，行数零丢失）

| 项 | 内容 |
|---|---|
| 证据 | 9.53GB / 99,999,981 行：**注入成功（行数与源文件完全一致）**，耗时 **11,427s（3h10m）**，吞吐 **8,752 行/s**；WS 峰值 ~8GB，无 OOM |
| 对照 | 1 千万行 215.8s（46K 行/s）、1 百万行 20.2s（49K 行/s）→ 亿级档吞吐约为 1/5 |
| 根因 | 单事务 + 固定 `batch_rows=1000 / batch_bytes=4MB`（`transfer_stream.rs:20-22`）逐批写入；行数越多，事务日志与回滚段压力越大，commit 前所有连接不可见（这解释了"中途查不到行"） |
| 不修的后果 | 用户导入 >5GB 文件需等数小时且**中途无任何可见进度**（库里查不到行是单事务正常表现，但用户会以为卡死）；取消则整批回滚，几小时白等 |
| 改动成本 | **中大**。方向一：按块提交（牺牲原子性，须产品决策并明示用户）；方向二：解析/写入流水线化 + 更细的进度回报。涉及事务语义变更 |
| 短期缓解 | 对 >1GB 文件在向导里给出"预计耗时约 X 分钟"提示（低成本，避免用户误判卡死） |
| 备注 | 此前"111 分钟零插入/不可用"的说法已作废——那是单事务的正常不可见性，不是失败 |

## 二、B 类：功能缺失/行为不符预期（按需决定）

### B1. SQL Server 备份未实现 —— ✅ 确认（代码中确实无实现）

不修后果：SQL Server 用户点备份得到"尚未实现"，**只能改用转储 SQL 文件**（功能等价但非原生备份）。
成本：中（需要 T-SQL BACKUP DATABASE 实现 + 路径权限模型）。**建议：要么实现，要么把入口对 MSSQL 隐藏**（后者只需几行，避免用户撞墙）。

### B2. 达梦（DM8）多语句批量执行 `Unsupported SQL type` —— ⚠️ 需现场复验

报告记录为第二轮发现、之后再未复验（第三/四轮无达梦环境）。代码里 JDBC 走 `Db::Http` 旁路，
推测与 JDBC sidecar 的类型映射有关。不修后果：**达梦用户无法用"运行 SQL 文件"**，只能逐条执行。
成本：中（需要达梦实例 + JDBC 链路调试）。**建议：先在 box 上用 1.0.2 复验是否仍存在，再决定**。

### B3. PostgreSQL「仅结构」转储产出空壳文件 —— ⚠️ 需复验

第二轮发现（选择"仅结构"时产出文件无内容）。代码中 `transfer.rs` 的 `structure_only` 分支存在，
需实际跑一次确认是否已随后续重构修复。不修后果：PG 用户"仅导结构"得到空文件，**误以为成功**（比报错更危险）。
成本：小（若确认是分支写漏）。**建议：优先复验，因为静默产出空文件属于高危误导**。

### B4. 同步向导"上一步"重置连接选择 —— ⚠️ 需复验

第二轮发现。不修后果：用户改配置要重填，体验差但不致错。成本：小~中（SyncDialog 状态保持）。

### B5. 还原进度 UI 停滞、无完成提示 —— ⚠️ 需复验

第二轮发现；数据实际恢复成功但 UI 不更新。不修后果：用户以为没还原成功，**可能重复执行还原**（有风险）。成本：小~中（进度回调）。

### B6. 树缓存 `refreshTree()` 不刷新已展开节点 —— ✅ 确认（本轮自动化实测仍在）

证据：第四轮测试中建表后树不出现新表，必须折叠/重开连接（我的 6 次自动化尝试都卡在这）。
不修后果：**用户建表/建库后看不到新对象**，以为操作失败。这是第四轮实测中实际消耗最多时间的产品障碍。
成本：小（第三轮已修"折叠时失效缓存"，现在只需让 `refreshTree` 走同一失效路径）。**建议：性价比最高的一条**。

### B7. `localhost` 解析到 `::1` 导致同步连接失败 —— ✅ 确认（设计取舍）

现状：只做错误分类与提示，**不做自动回退**（开发侧明确论证过：自动换地址可能改变认证/TLS 语义）。
不修后果：目标是本机 MySQL 时，同步向导默认可能连 `root@'::1'` 被拒，用户需手动改 `127.0.0.1`。
成本：若做自动回退属于**高风险改动**（改变连接语义）。**建议：不修，保持现状**；若要改善，只在向导默认值里把本机地址写成 `127.0.0.1`（低风险）。
