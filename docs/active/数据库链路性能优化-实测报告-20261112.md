# 数据库链路性能优化 · 实测报告（2026-11-12）

关联计划：[database-performance.md](database-performance.md)

## 1. 范围

数据同步、运行 SQL 文件、备份导出/还原三条链路。以真实 MySQL / PostgreSQL 实例前后对照为准。

## 2. 瓶颈定位（改动前）

| 链路 | 原实现 | 瓶颈 |
|---|---|---|
| 运行 SQL 文件 / 还原备份 | src-tauri/src/transfer.rs 逐条语句、每条单独提交（autocommit），MySQL 分支还逐条从连接池取连接 | 每条 INSERT 一次隐式事务刷盘（双写+redo/WAL），2000 条语句约 39 s，约 19 ms/条 |
| 数据同步（全量） | src-tauri/src/sync.rs 只有 SQLite 合并多行 INSERT；MySQL/PostgreSQL 一行一条 INSERT | 每行一次协议往返 + 语句解析，20000 行约 10 s（约 2000 行/s） |
| 数据同步（读取） | 分页用 LIMIT n OFFSET m | 深页扫描前 offset 行，大表 O(n²) |
| 备份导出 | src-tauri/src/transfer.rs 流式游标，逐行写单行 INSERT | 导出本身较快；文件体积与还原语句数偏大（本次未改格式） |

## 3. 改动

1. run_sql_file_detailed / restore_sql_file_detailed：改为固定单物理会话逐条执行；连续 DML 攒成批事务，每 1000 条或 8 MiB 提交一次；遇到 DDL/SET 先提交再自动提交执行，保持「DDL 立即生效」；批内失败回滚该批并在错误中写明回滚条数。会话级守卫（SET FOREIGN_KEY_CHECKS / PRAGMA foreign_keys / SET session_replication_role）因此真正作用于整段脚本。
2. InsertSpec::statements 的批量判定：MySQL/PostgreSQL 目标表无触发器时也合并多行 VALUES（256 行 / 1 MiB 一条语句），与 SQLite 现有策略对齐。
3. SyncPageFeeder 有主键时改键集分页（(k1,k2) > 上一页末行），无主键回退 OFFSET；新增 fetch_transfer_page_after。

- [sync.rs](../../src-tauri/src/sync.rs)

## 4. 实测结果

环境：Windows 本机，MySQL 8.0.44（innodb_flush_log_at_trx_commit=1、autocommit=1）、PostgreSQL 16.15；单表 id BIGINT PK, v VARCHAR(200), amount DECIMAL(20,4), note TEXT；2000 行；预热 1 轮丢弃，取多轮中位数；每次运行新建隔离库/模式并在结束时删除。

### 4.1 MySQL（2000 行，2 轮中位数）

| 用例 | 优化前 | 优化后 | 提升 |
|---|---:|---:|---:|
| 全量同步 | 1 090 ms | 245 ms | 4.4× |
| 运行 SQL 文件（2000 条 INSERT） | 39 138 ms | 580 ms | 67× |
| 备份导出 | 52 ms | 59 ms | 约 1×（未改动） |
| 还原备份（2000 行） | 37 996 ms | 674 ms | 56× |

吞吐：运行 SQL 文件 51 → 3 447 行/s；还原 53 → 2 965 行/s。

### 4.2 PostgreSQL（2000 行，5 轮中位数）

| 用例 | 优化前 | 优化后 | 提升 |
|---|---:|---:|---:|
| 全量同步 | 309 ms | 83 ms | 3.7× |
| 运行 SQL 文件 | 1 331 ms | 457 ms | 2.9× |
| 备份导出 | 同量级（未改动，波动为主） | | |
| 还原备份 | 2 019 ms | 895 ms | 2.3× |

### 4.3 大表键集分页（MySQL，100 000 行 / 50 页）

| 分页方式 | 全量同步 | 吞吐 |
|---|---:|---:|
| OFFSET 分页 | 9 556 ms | 10 465 行/s |
| 键集分页 | 3 713 ms | 26 928 行/s |

10 万行时 2.6×；OFFSET 成本随行数平方增长，行数越大差距越大。

### 4.4 原生客户端参照（同一份 2000 条 INSERT 脚本）

| 执行者 | 2000 条 INSERT 耗时 |
|---|---:|
| mysql 8.0 命令行客户端 | 215 ms |
| psql 16 客户端 | 949 ms |
| 本产品优化后（MySQL） | 580 ms |
| 本产品优化后（PostgreSQL） | 457 ms |

说明：本产品每条语句都返回可视化的逐条结果（影响行数、错误定位），命令行客户端不做结果收集。优化后已在同一量级：PostgreSQL 快于 psql，MySQL 约为 mysql 客户端的 2.7 倍（每条语句约 0.29 ms，主要是结果收集与 SQLx 逐条往返开销）。

## 5. 语义与安全边界

- 批事务只合并连续 DML；DDL/SET/事务控制语句仍逐条自动提交，「每条 DDL 立即生效」不变。
- 批内失败：回滚当前批（最多 1000 条）并如实报告回滚条数；更早批次已提交。比原先「失败前每条都已单独提交」更少半套数据。
- 会话级外键守卫现在与数据落在同一会话（原先逐条从池取连接，守卫可能作用于别的会话）。
- MySQL DDL 会隐式结束事务，因此实现遇到非 DML 先提交，下一段 DML 再显式开启，避免「以为在事务里其实已自动提交」。
- 非事务通道（SQL Server/ClickHouse/ODBC）保持逐条执行并如实提示失败不回滚。
