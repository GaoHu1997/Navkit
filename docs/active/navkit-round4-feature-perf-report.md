| 维度 | 结果 |
|---|---|
| 功能矩阵（12 项 × MySQL） | **12/12 通过**（界面化建库建表/查询/视图/关系图/设计表/数据同步/数据生成/数据字典/运行SQL文件/转储SQL文件/导入/导出） |

| 数据生成 | 向导全流程（预览冻结→确认→单事务写入）功能验证通过；大行数向导吞吐未测得（见 §6 未完成项） |

**本轮新发现缺陷**（均含复现证据）：

| 编号 | 严重度 | 问题 |
|---|---|---|
| D-R4-1 | **高** | `count_query_page` 在 MySQL 上类型解码失败：`Rust type Option<String> (as VARCHAR) is not compatible with SQL type BIGINT` → 查询服务器分页总行数永远"统计中"，**页码跳转/末页按钮永久禁用**；1万→1亿全部量级复现 |
| D-R4-2 | **中** | Keyset 锚点链路未激活：查询与表数据的"下一页"实际均走 `LIMIT/OFFSET`（SQL 日志证实）；`serverPageAnchor` 始终 null，`plan_query_keyset_page` 未生效（与 D-R4-1 的失败链路疑似相关） |
| D-R4-3 | **中** | s1m（100万行）表数据网格总数异常：末页被钳到 offset 500000（应用内总数≈50.1万，实际 100 万），跳页读数 firstId 与 pageOffset 不一致一次；后续依赖 count 的行为需复查 |
| D-R4-4 | **低** | 数据字典向导第 4 步的"文档名称不能包含 \ / : * ?"校验提示在字段修正后不清除（陈旧错误文案滞留，不影响最终导出成功） |
| D-R4-5 | **中（性能）** | 亿级单文件导入吞吐塌陷：1 千万行 46K 行/s → 1 亿行降至 **8.7K 行/s（3.2 小时）**；行数零丢失、无 OOM，但等待时间不可接受（详见 §5.1） |

> 勘误：测试初期曾记录"933MB 导入导致应用进程死亡"——经逐项排查为**测试基建自身事故**
> （文件路径被 shell 转义破坏 + 后续探针的 launchApp 误杀前一实例 + DROP 表导致的陈旧计数），
> **撤回该结论**。1000 万行批量导入实际成功（215.8s，46,346 行/s，库侧 10,000,000 行核验一致）。

**前轮缺陷回归**（第三轮遗留项在本轮的观察）：
- **D7 跨库转储删源表：未复现**（本轮表级转储与整库转储均在同库/跨库目标上执行，未观察到源库数据被删；建议在专用跨库还原场景再确认一次）
- **D5 树缓存**：仍在（`refreshTree()` 不刷新已展开节点的子树，需折叠/重开连接；本轮自动化被迫绕行）
- **D11 USE 文件拒绝 / D9 ::1 / D10 类型膨胀**：本轮未复测（未在测试范围内构造对应场景）

## 3. 查询分页性能（v1.0.2 服务器分页，每页 200 行）

| 表（行数） | 首页 | 顺序翻页 ×5 | 走页至 50 页 | 回翻首页 | 深跳/末页 |
|---|---|---|---|---|---|
| s10k（1万） | **0.11s** | 0.20–0.22s | 1.4s（8 页） | **缓存命中，0 次 IPC** | ⛔ D-R4-1 |
| s100k（10万） | **0.15s** | 0.20–0.22s | 11.1s | 缓存命中 | ⛔ |
| s1m（100万） | **0.09s** | 0.20–0.21s | 10.8s | 缓存命中 | ⛔ |
| s10m（1000万） | **0.11s** | 0.20–0.22s | 11.2s | 缓存命中 | ⛔ |
| **s100m（1亿）** | **0.10s** | 0.20–0.22s | 11.4s | 缓存命中 | ⛔ |

要点：
- **首页延迟与表行数无关**（1万→1亿 均 ≤0.23s）——服务器分页只取当前页。
- **顺序翻页耗时恒定**（窄表 0.2s、宽表 0.35s），已看页缓存回翻零 IPC——大结果集浏览体验稳定。

  因此"深分页 OFFSET vs Keyset"在查询模式下无法测量；替代路径为表数据网格（见 §4）。

### 5.1 亿级导入（s100m.csv 9.53GB → impb_100m）—— ✅ 完成，但耗时 3.2 小时

| 观测 | 值 |
|---|---|

## 7. 缺陷详情与修复建议

### D-R4-1 count_query_page MySQL 解码失败（高）
- **现象**：查询服务器分页执行后，后台总行数统计始终失败；状态"总行数未知/统计中"；
  页码输入与末页按钮永久禁用（`aria-description="服务器分页总数统计中，返回后可跳页"`）。
- **错误原文**：`error occurred while decoding column 0: mismatched types; Rust type Option<String> (as SQL type VARCHAR) is not compatible with SQL type BIGINT [code=QUERY_FAILED]`
- **复现**：s10k/s100k/s1m/s10m/s100m/wide100 全部复现（1万→1亿），100% 复现率。
- **影响**：v1.0.2 查询页的核心新功能（总行数统计 + 跳页 + 末页）在 MySQL 桌面端不可用。
- **建议**：检查 `count_query_page` 的 sqlx 行解码映射（COUNT(*) 列被声明为 String 期望）；
  按 PRODUCT-STATE 记载该功能"真实 MySQL 端到端 1 项通过"，但桌面全量级实测失败，需对齐两处差异（连接参数/SQL 形态）。

### D-R4-2 Keyset 未激活（中）
- **现象**：查询"下一页"与表数据"下一页"实际均执行 `LIMIT/OFFSET`（SQL 日志证据：
  `SELECT * FROM navkit_p4.s100m LIMIT 200 OFFSET 10000`）；`serverPageAnchor`/`next_after` 始终空。
- **影响**：Keyset 分页（1.0.2 核心卖点之一）在 MySQL 上未生效；OFFSET 代价在深页线性增长
  （本测试主键序表 + 热缓存下不显著，乱序/冷缓存场景风险更高）。
- **建议**：排查 `plan_query_keyset` 的单列唯一主键判定在 MySQL 的返回路径。

### D-R4-3 s1m 网格总数异常（中）
- **现象**：s1m（实际 100 万行）表数据页的"最后一页"跳到 offset 500000（≈50.1 万总数）；
  同表跳页读数 firstId 与 pageOffset 出现一次不一致。
- **建议**：复查表数据 `countTotal`（`include_total:true` 的 page_table）路径；捕获 grid 页脚 countText 增加断言。

### D-R4-5 亿级导入吞吐塌陷（中/性能）
- **实测**：9.53GB / 99,999,981 行，11,427s（3h10m），吞吐 8,752 行/s；行数与源文件完全一致。
- **对照**：1 千万行 215.8s（46K 行/s）、1 百万行 20.2s（49K 行/s）——随规模出现约 5× 衰减。
- **建议**：分块提交（需产品决策牺牲原子性）或解析/写入流水线化；短期对 >1GB 文件给出耗时提示。

### D-R4-4 字典向导陈旧校验文案（低）
- **现象**：文档步骤的"文档名称不能包含…"错误提示在字段修正为合法值后不清除，滞留显示。
- **影响**：仅提示噪声（导出最终成功）。
