## 1. 性能回归对比（MySQL，50 表 / 20,210,000 行 / 单表 250 万）

| 场景 | 第二轮（1.0.0-pre） | 第三轮（1.0.0） | 变化 |
|---|---|---|---|
| 运行 SQL 文件（1.21GB / 20,310 语句 / 20,210,000 行） | 990.3s，20,408 行/s | **848.3s，23,973 行/s** | **+17% 吞吐提升** ✅ |
| 转储全库（3.4GB / 51 表 / 20,210,000 INSERT） | 183s，RSS 低 | 262s，RSS ~297MB 稳定 | 略慢，无 OOM ✅ |
| 备份全库（3.4GB） | 276s 完成→**完成时 OOM** | **710s 完成，RSS 峰值 ~507MB，无 OOM** | 慢 2.6 倍但正确 ✅ |
| 导入 CSV（250 万行 / 152MB） | **~200 万行处 OOM，数据全丢** | **完成，2,500,000 行全部提交**（RSS 峰值 1.41GB 平台） | 慢（11.7K→4K 行/s）但正确 ✅ |
| 大查询（250 万聚合 + 8 表 2000 万 COUNT） | 12.6s | 11.6s | 持平 ✅ |
| 同构同步（250 万行 big_1→copy） | 未测（内存顾虑） | **~210s ≈ 11,900 行/s** | 新增测量 ✅ |

**性能结论**：1.0.0 以流式化改造解决了内存爆炸（备份/导入不再 OOM、RSS 有界），
代价是备份/导入吞吐下降 2-3 倍；运行 SQL 文件吞吐反而提升 17%（23,973 行/s）。
同步 250 万行实测 11,900 行/s，均无内存风险。

## 2. 回归明细

### 2.1 D16 查询页锁死 — ✅ 已修复
打开 R2-MySQL→浏览元数据→新建查询→`SELECT * FROM t_crud; SELECT COUNT(*) FROM t_types;` 一次通过
（0.650s，结果 1 = 2 行）。round 2 的「事务/活动命名空间…此次没有发送」未再现。

### 2.2 D15 密码泄露 — ✅ 已修复（附 UX 改进）
新建连接（localhost:3306/root，密码留空，保存密码勾选）→ 点测试连接：
1.0.0 **不再发送任何密码**，改为提示「请输入密码；若服务器允许无密码认证，请勾选『使用空密码 / 无密码认证』后再测试」，
且对话框新增「使用空密码 / 无密码认证」勾选框。勾选后重测：发送真空密码（Access denied 证实，非 keystore 密码）。

### 2.3 P2-R 内存 — ✅ 已修复（流式化）
- 备份 51 表：`navkit_perf_20261115_013658.sql` 3.4GB 生成于
  `~/.local/share/navkit/backups/`（**新路径：用户目录，第二轮 P10 安装目录问题同时修复**），
  710s；写出期间 RSS 403-507MB；**完成时无 OOM**（第二轮完成瞬间冲 2.39GB 被 OOM）。
- CSV 导入 250 万行：向导解析 152MB CSV → 单事务写入 → **全部 2,500,000 行提交成功**
  （id 1..2500000 连续，抽样数据正确）；RSS 曲线 615→1411→**稳定 1380MB**（第二轮爬至 2.3GB 崩溃）；
  dmesg 无新增 OOM（全部 5 条 OOM 记录均为 11-12/13 日第二、一轮遗留）。

### 2.4 D1 空间类型 — ✅ 已修复
POINT 列网格显示 `SRID=0;WKB=0x0101000000000000000000F03F0000000000000040`（即 POINT(1 2)），
值可读不再丢失；c_blob/c_json/c_enum/c_set 全部正确。

### 2.5 P7-R 字典文件名 — ✅ 已修复
输出路径 `/workspace/navkit-test2/dumps` → 文件正确落盘
`dumps/navkit_r2数据库设计文档20261114235411.md`（2.7KB，3 表）。
（第一、二轮的反斜杠文件 `dumps\xxx.md` 均为旧版遗留文件。）

### 2.6 D7 转储库名 — ❌ 未修复（破坏性复现）
1.0.0 转储文件仍为 `DROP TABLE IF EXISTS \`navkit_r2\`.\`t_crud\`` / `INSERT INTO \`navkit_r2\`...`
而 `CREATE TABLE \`t_crud\`` 不带库名。导入 verify_r2 实测：
`ERROR 1146 Table 'navkit_r2.t_crud' doesn't exist`，**源库 navkit_r2 的 t_crud 被删空**，
verify_r2 仅留空表（与第二轮一致）。

### 2.7 D11 USE 文件 — ❌ 未修复
含 `CREATE DATABASE/USE` 的 245 字节文件仍被拒：
`执行失败（代码 BATCH_SQL_PARSE_FAILED）…原因：SQL 不能改变数据库/身份/服务器授权范围`。

### 2.8 D9 ::1 — ❌ 未修复
同步向导默认目标连接仍报 `Access denied for user 'root'@'::1'`；无 127.0.0.1 回退。

### 2.9 D10 类型膨胀 — ❌ 未修复
同步自动建表 `navkit_r2_copy.big_1`：`int→bigint`、`decimal(12,2)→decimal(65,20)`、
`datetime→datetime(6)`（与第二轮一致）。

### 2.10 新回归：转储被 YEAR 列阻断 ⛔
1.0.0 转储含 `c_year YEAR` 列的表报：`导出列 c_year (YEAR) 尚不能无损解码，未将非 NULL 值伪造为 NULL`。
**1.0.0-pre 时同表（含 YEAR/POINT）转储成功**——转储类型覆盖出现回归（空间类型改善的同时 YEAR 新增阻断）。
删除 YEAR 列后转储成功（3.1KB / 3 表）。建议与 PG 的不可解码类型白名单一并对齐。

### 2.11 其他观察（正面）
- 关闭连接时新增「未保存的修改…离开后会丢弃」确认框（防误丢 SQL 编辑）。
- 连接断开后旧页显示「连接已断开，旧页暂存。SQL 编辑仍保存；重新选择连接才会重连。」+ 恢复流程清晰。
- 备份文件改存 `~/.local/share/navkit/backups/`（第二轮 P10 安装目录问题修复）。
- 后台任务中心列出全部历史任务及结果（成功/失败+原因）。

## 3. 修复优先级建议（更新）
