# 文档生命周期

`docs/` 只有三条线和一份常驻输入。任何文档都必须属于其中一条，不存在「先放根目录再说」。

## 1. 目录契约

| 路径 | 内容 | 硬约束 |
|---|---|---|
| `docs/completed/` | **只有结果**，通常是 `PRODUCT-STATE.md` 一份 | 每条能力必须带可打开的代码入口；不含过程细节、不含历史 ROI、不含未验证的乐观描述 |
| `docs/active/` | 进行中的详细过程文档 | 每份必须有验收标准；允许长、允许带证据日志 |
| `docs/active/evidence/` | 被 active 文档按行号引用的跑批日志 | 只增不改；日志名保持原样 |
| `docs/planned/` | 尚未开始的工作 | 必须有范围、非目标、进入条件；不得含已开工内容 |
| `docs/design/` | 常驻设计输入：设计系统、界面规格、原型 | **不搬动**——源码注释按 `docs/design/...` 路径引用它 |

## 2. 准入

- 开工前：写一份计划文档到 `docs/planned/`，含范围、非目标、验收标准、代码触点。
- 一旦有代码改动落在工作树：把这份文档移到 `docs/active/`。`planned/` 里不留已开工项。
- 过程中新增的测试报告、根因分析、修复方案：`docs/active/<主题>/NN-*.md`，证据放同目录 `证据/` 或 `evidence/`。

## 2.1 证据目录的硬上限

`active/` 堆满日志就是这条线失守的开始。三条上限：

1. **`evidence/` 只放被 active 文档按行号引用的日志。** 交付前跑一遍：
   `grep -rho 'evidence/[A-Za-z0-9._-]*\.log' docs/active/**/*.md docs/active/*.md | sort -u`
   不在结果里的 `.log` 一律删除。日志是过程产物，结论进了报告它就没有留存价值。
2. **同一轮测试重复运行只留最新一轮完整证据。** `round1-desktop-<uuid>/` 这类每次运行生成一个目录的，
   只保留最新一轮的截图/事件/DOM，其余目录只留 `report.json`、`assertions.json`、`manifest.json`。
3. **`active/` 的总文件数要能说清。** 交付前报一次构成：任务书 N 份、日志 M 份、证据 K 份；
   M 或 K 讲不清来源就是没清干净。

## 2.2 active 只放当前轮次

`active/` 的体积就是「还有多少事没完」的度量。三条：

- 常驻的只有跨任务契约（如 `00-交接规范与公共契约.md`）与当前轮次的报告。
- 上一轮的报告在结论并入结果文档后删除，不留「已完成待归档」的中间态。
- `active/README.md` 用一张表列出当前内容与状态，超过 5 行说明该归档了。

## 3. 完成判定（开发完成即归档）

**归档看开发，不看验收。** 代码落地 + 对应测试存在，就够格进 `completed/`；等真机或专用实库
会永久卡住归档，让 `active/` 变成任务堆积场。

归档前必须有：

1. **代码入口存在**：结论里提到的每个模块/命令，路径能打开。
2. **测试存在**：给出可复现命令与最近结果；失败项如实写失败，不能把「单跑通过」写成「通过」。
3. **验收状态标清**：三选一，写在结果文档的能力行里——
   - `✅` 有真实服务器/真实桌面的通过证据
   - `⏳` 代码完成，缺真机或专用实库的现场验收
   - `🚧` 仍有已确认的功能缺口

标 `🚧` 的条目必须在结果文档的「已知限制」里留一条待办，并在 `active/` 保留对应的当前轮次文档。
标 `⏳` 的条目直接归档，不需要留在 `active/`。

## 4. 完成动作（一次做完，不留半成品）

1. 把 `active/` 文档里的**结论**合并进 `docs/completed/PRODUCT-STATE.md`：能力行、代码入口、验收状态、边界。
2. 任务书类文档补进「实现归档」表：ID / 任务 / 已落地 / 待办。
3. **删除过程文档**。只有细节没有结论的直接删；证据日志移入 `active/evidence/` 或随之删除
   （先确认别处没有按行号引用）。
4. 更新 `PRODUCT-STATE.md` 顶部的「最后核对」日期与代码基线。
5. 在「文档来源合并记录」追加一行：原件名 + 合并了什么。

`completed/` 里出现第二份过程文档，就是这一步做错了。

## 5. 一致性闸门（每次改代码后跑）

```bash
# 1. 文档提到的代码入口是否还在
python tools/check-doc-links.py

# 2. 相对链接层级是否正确（docs/active/ 下是 ../../src-tauri）
grep -rn '](<\.\./src-tauri' docs/active/*.md

# 3. 类型与构建
npm run build
cargo check --manifest-path src-tauri/Cargo.toml --lib --offline
```

`check-doc-links.py` 扫描 `docs/**/*.md` 里的 `` `path/file.rs` `` 与 `](<path>)` 形式，逐条 `os.path.exists`，
把缺失项打到 stdout 并以非零退出。任一缺失 → 修文档，不要删检查。

## 6. 反模式

| 症状 | 纠正 |
|---|---|
| `completed/` 里出现带「本轮」「待复核」的文档 | 那是过程文档，留在 active |
| 结果文档写「已实现全部 25 项」 | 按证据逐条写，未闭环的进边界列 |
| 把跑批日志直接删掉 | 先查 `grep -rn '\.log' docs/`，被引用的移入 evidence |
| 移动文档后不修链接 | 相对路径层级变化必须整体重算，跑一遍闸门 |
| 把 `docs/design/` 搬进三阶段目录 | 源码注释会断，禁止 |

## 7. 迭代日志

规则本身也受版本管理。每次发现本 skill 漏掉的场景，在下面追加一条，并同步修正对应章节。

- 2026-11-11｜建立：三阶段目录、完成三要素、合并后删除过程文档、一致性闸门。
- 2026-11-11｜首次执行后修正：迁移时把 `plan/` 与 `.tmp/` 的全部日志无条件搬入 `active/evidence/`，
  249 份里只有 33 份被文档引用，`active/` 因此涨到 47 MB。补 §2.1 证据硬上限；清理后 6 MB。
  教训：搬证据之前先问「谁引用它」，不是「它原来在哪」。
- 2026-11-11｜门槛修正：原先要求「验证通过」才归档，导致 25 项全部卡在 `active/`、永远归档不了。
  改为**开发完成即归档**，验收状态用 ✅/⏳/🚧 记入结果文档；`🚧` 才需要保留 active 轮次文档。
  25 份任务书并入 `PRODUCT-STATE.md` §五 后删除，`active/` 从 36 份文档降到 3 份。
  教训：用「验收」当归档门槛，等于把缺环境变成久拖不决的堆积。
